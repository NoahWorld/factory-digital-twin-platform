# 厂房场景架构评估与技术选型

记录日期：2026-09-09。

## 场景与结论

目标：用户在车间/厂房内部查看、漫游，点击设备后在当前页面以 2D 面板展示关键数据；模型数量在目标浏览器和硬件的可承受范围内。

现有 React + TypeScript + Vite + Three.js 可以继续使用。主要缺口是场景运行管理、资产绑定粒度、室内导航、模型处理和共享实时数据层，不是前端框架或渲染引擎选择错误。浏览器没有一个通用的“模型数上限”：性能取决于网格提交、三角面、纹理显存、动画、分辨率、交互和设备硬件。

本评估基于当前工作区源代码，包括尚未提交的独立 3D 功能；不是线上验收结论。尚无真实厂房模型压测结果，不承诺帧率、首屏时间或最大设备数。

## 评估时的基础与局限

### 可以保留的设计

- 单个场景共享 renderer、相机、灯光、控制器和动画循环。
- 同一模型资源在场景内解析一次，克隆复用几何和原始材质。
- 模型、资产、数据与画布通过稳定业务 `assetId` 关联；数据库记录 ID 不代替业务编号。
- 独立 3D 使用规范化实例记录和修订号，不把完整模型树嵌入 2D JSON。
- 资源释放、真实错误、服务端权限与预算校验保留。

### 需要解决的问题

1. **室内导航**：原有 OrbitControls 是围绕目标查看；本轮已增补 Rapier 静态角色控制器，但现有项目尚未接入碰撞配置制作与保存。需要行走高度、碰撞、地面、可通行区域、入口、复位和视角保存。普通布局调整、灯光变化和模型增删不应强制将用户拉回全景。
2. **2D/3D 运行闭环**：独立 3D 目前发送选择事件并提供关联 2D 页面入口，卡片只显示资产元数据。2D 的本地 REST 竖切仍要求恰好一个 3D 组件、资产有 modelNode 且不超过 50 个资产，不能作为独立 3D + 纯 2D 浮层的通用数据服务。
3. **绑定粒度**：独立场景目前按整个实例绑定资产。整厂 GLB 内的设备需要“实例 ID + 稳定节点标识 → assetId”映射。同一模型的多次复制不能仅凭相同节点名关联。长期资产台账应由 2D/3D 共享，而不是依附某一显示页面。
4. **资源生命周期**：评估时批量场景所有唯一模型并发加载，全部成功后组装；实例资源结构变化触发 renderer 和资源整体重建。需改为受控加载、增量实例更新和明确资源所有权。
5. **渲染与拾取**：几何复用不等于 GPU Instancing；大量复制仍会增加绘制调用。缺少区域管理、距离 LOD、区域卸载和拾取加速。默认视锥裁剪不等于区域流式加载或墙后遮挡管理。
6. **预算准确性**：文件压缩体积不等于 GPU 内存；glTF meshes 数量不等于最终网格引用次数、primitive 数量或绘制提交。需补充三角面、纹理尺寸/格式、动画轨道/骨骼及运行测量。
7. **实时数据**：浏览器逐资产请求，服务端按请求即时采集，同源多资产及多用户会重复访问上游。应改为按数据源集中采集、资产快照缓存、批量分发和前端按资产订阅。
8. **发布与交付**：2D/3D 独立修订需要可追溯的发布组合、资源版本和回滚；现场运行需要断线恢复、长时验证、日志与性能证据。

评估时独立 3D 预算：128 个实例、24 个唯一模型、150 MiB 唯一模型文件、6,000 个估算网格实例、开启动画时 24 个动画实例、单补丁 100 个实例变更；上传单模型 25 MiB。这些是保护性配置限制，不是性能保证。参见 `shared/standalone-3d.ts` 和 `apps/api/src/model-assets.ts`。

## 技术选型决定

| 层次 | 决定 | 理由与边界 |
| --- | --- | --- |
| UI | 保留 React / TypeScript / Vite | 继续复用编辑器与 2D 组件 |
| 渲染 | 保留 Three.js / WebGLRenderer | 当前缺口可在现有引擎内解决；WebGPU 等硬件压测证实收益后评估 |
| React 与 3D 边界 | 独立 SceneRuntime，React 只负责挂载、配置、UI 与事件桥接 | 高频状态不通过 React 每帧 setState 驱动；R3F 不是必需性能升级 |
| 资源管理 | ResourceManager + 有界并发 + 引用计数 + 取消/释放 | 实例增删不重建 renderer；复用资源并保留失败上下文 |
| 实例与空间管理 | InstanceManager、区域清单、InstancedMesh；适当场景评估 BatchedMesh | 静态重复设备可实例化；骨骼动画、节点检视与材质覆写需独立路径 |
| 拾取 | 区域/实例包围盒筛选 + three-mesh-bvh | 保留建筑遮挡；不要通过忽略墙体制造穿墙选择 |
| 行走 | 已接入 Rapier 0.20.0 JavaScript/WASM 角色控制器 + 显式简化长方体碰撞配置 | 渲染、拾取和碰撞分别管理；项目配置编辑/保存、真实厂房验收仍待完成 |
| 模型链路 | glTF Transform + Meshopt + KTX2/Basis | 前端接解码器；优化任务属于后端/离线流水线，保留来源、参数、检查报告与稳定节点映射 |
| 运行数据 | 独立资产状态仓库，REST 初始快照 + SSE 状态增量 | 只读展示优先 SSE；频繁双向协议出现时再选 WebSocket；需快照、序号、重连与陈旧状态 |
| 现场后端 | Node.js / TypeScript / Fastify | 模块化单体 API + 独立采集和模型任务进程 |
| 数据与对象存储 | PostgreSQL + S3 兼容适配器 | D1/R2 保留云端验证用途；配置与历史时序存储分别规划 |

后端迁移不是仅更换连接串：现有 DB/ObjectBucket 接口仍有 D1/R2 语义，必须迁移 SQL、事务、存储元数据和认证运行时差异。Redis/专用时序存储按多进程分发或历史数据规模决定，不作为当前必需组件。

## 前端目标边界

```text
React 编辑器 / 2D 数据面板
       │ 配置、选择事件、低频状态
       ▼
SceneRuntime ── 导航控制 / 诊断
       ├── ResourceManager → 本地解码器 → GLB/GLTF
       ├── InstanceManager → Object3D / 后续静态批处理
       └── PickingService → 包围盒 / BVH → 实例与节点标识

共享资产状态仓库 → 2D 面板 + 3D 外观增量
       ▲
现有 REST API；后续接服务端快照与 SSE
```

同一个设备根据需要有显示模型、命中代理和简化碰撞体。碰撞体不应从每个可见零件自动生成。区域清单需定义稳定 regionId、边界、资源引用、LOD 资源、碰撞资源和实例归属；持久化契约必须与后端统一，不能先在浏览器私存另一套配置。

## 本次实施约束

用户决定：先调整和补充前端架构及技术内容，后端搁置。

- 当前先落地运行层拆分、增量实例和资源生命周期、本地压缩模型解码、拾取加速、相机稳定性与诊断。
- 不修改后端/API/schema/采集器/数据库；不把尚未实现的 SSE、模型优化服务或漫游碰撞写成可用功能。
- 具体已完成内容、检查命令与剩余前端事项见 [前端场景运行架构](./frontend-scene-runtime.md)。

## 验证与后续顺序

1. 自动化验证加载复用、并发、取消、失败恢复、实例增删与释放；前端类型检查与生产构建。
2. 用真实/脱敏厂房模型验证首屏、帧耗时分位数、绘制调用、三角面、纹理、点击延迟、区域切换和多小时内存走势。
3. 在共享资产与接口契约明确后，实现原地实时 2D 数据面板与实例内部节点绑定。
4. 将已接入的 Rapier 行走与真实项目碰撞数据对齐，补齐配置编辑/保存；再推进按区域 LOD/卸载和合适设备的 GPU Instancing；逐项测量，不能只提高硬上限。
5. 用户恢复后端工作后，再做模型处理任务、集中采集与分发、现场数据库迁移和发布版本组合。
