# M3 场景与资源实现路线

M2 本地提交 `e8051e4` 已保留。继续完整引擎目标，M3 不单独关闭目标。

复用当前三维渲染、资源上传/内容接口、Model3DInspector 和项目编辑上下文。先修复共享资源加载与释放，再把单模型适配为可复用 SceneDefinition；多模型属于同一个 renderer 的实例根，不使用重叠的三维组件冒充多模型场景。

项目定义增加场景列表，同项目 CAS 保存独立 `project_scenes`。场景拥有环境、灯光、相机和实例；实例固定引用不可变的 model_assets.id，拥有稳定实例 ID、变换和对象覆盖。画布只引用 sceneId。同一场景可被多个页面引用，显式复制场景才产生独立配置。

对象清单使用源稳定标识或首次分配的 objectId，版本清单负责关联实际 glTF 对象。名字只在单一文件版本中定位，索引路径只在会话中定位。模型更新保留旧资源版本，显示缺失/重命名/歧义及影响，修复后以一次可撤销项目操作更新引用。旧单模型及 assets.model_node 保留兼容，新资产映射使用 sceneId/instanceId/objectId，允许同名模型的不同实例绑定不同设备。

首个场景验收：旧单模型提取为场景→另一页关联→增加同模型实例和第二种模型→独立调整位置/材质→保存重开/撤销→两页一致更新。再验证独立场景副本不串联、实例资产映射、模型版本替换和引用修复。

资源验收先覆盖并发相同资源只加载一次、对象实例独立但几何和纹理共用、最后消费者释放全部资源、加载取消后的迟到结果释放、失败可重试。浏览器重复进入/退出观察实际缓存与渲染资源；M7 再扩大模型规模和长时测量。

模型导入检查优先复用 glTF Transform 的 WebIO、访问器和纹理尺寸解析，不手写完整 GLTF/GLB 解码器。官方接口支持内存 GLB/JSON，并默认严格检查缺失资源；安装前已核对核心 4.5.0 仅依赖 property-graph。保留现有外部 URI 禁止规则与不可变原始文件，报告基于真实解析结果，单位按 glTF 米制约定并明确无法据格式判断源导出器是否正确换算。来源：[WebIO](https://gltf-transform.dev/modules/core/classes/WebIO)、[glTF 2.0 规范](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html)。


资源检查已接入上传与旧资源补充检查。`@gltf-transform/core/extensions` 均锁定4.5.0，Worker使用WebIO读内存；最终产物确认不含NodeIO、node:fs、node:path。旧报告以CAS首次升级，固定对象UUID；同一资源后续检查不重分配。源extras.newpowerObjectId可作为后续版本匹配线索，不把名称或节点序号当作跨版本身份。

报告分别统计资源网格和默认场景放置后的三角面，包括EXT_mesh_gpu_instancing的实例数量与TRS；空间边界来自默认场景静态姿态的实际索引顶点。骨骼/形态动画边界明确不覆盖。纹理尺寸由真实内嵌图像解析；缺数据和非法格式被拒绝。glTF单位为米制约定，不能由格式证明导出器换算正确。

导入仍限25MiB原始文件；解码访问器按每分量8字节保守估算限256MiB，场景展开几何检查限2000万次顶点变换。后者防止小文件大量共享实例绕过唯一访问器预算；M7性能验证若需要调整，应按实测优化并记录，不静默忽略实例或返回低估报告。


统一渲染已落地：旧单模型以单实例适配进入同一SceneViewport。新场景按GLTFLoader的parser.associations把源nodeIndex对应到克隆对象，再关联报告objectId。实例增删仅获取/释放对应lease；已加载实例配置就地更新。材质按“原值→实例整体→对象覆盖→运行状态”应用，子对象覆盖在父对象之后；显隐与选择框共同遵守实例隐藏状态。

共享资源分两层：全局模型池复用解析，视窗内的几何/材质/纹理副本由ViewportResources引用计数；不同WebGL renderer不在同一Three资源上留下监听器。Geometry.clone会复制CPU几何数据，当前作为正确释放的明确代价，M7量测后优化。镜头首次就绪自动取景一次，后续变换/灯光不重置用户镜头；查看全部、定位实例、初始视角是显式取景入口。
