# M6a 集中采集与可移植运行基础

在 M4 本地验收后接续。现有 `collectAssetRuntimeState` 是按资产 GET 即时采集，浏览器 `ProjectRuntimeStore` 只在单页内去重；这不能证明多个客户端共享上游请求。REST 的超时、白名单、拒绝重定向、256 KiB 响应限制、字段/时间校验继续复用。WebSocket 与凭据解析目前还没有运行实现。

## 实施方向

采用可移植采集核心和本地 Node 宿主。现有 API 已使用标准 Request/Response，并抽象 Database/ObjectBucket；先在 `apps/runtime` 适配 SQLite、文件资源和同源静态服务，复用业务路由/权限及同一迁移目录，不另建一套项目API。宿主使用新的隔离运行目录，不直接转换 Worker 验收库；已有数据库升级继续先做实际备份和完整性检查。这个前置同时承接 M5 必需的独立运行基础，完整发布/打包仍归 M5。

集中采集按项目、数据源和配置代次组织，一次源请求服务所有相关资产映射与多个客户端。原始上游 JSON 只短暂留在服务端，客户只读标准指标和连接状态。编辑配置变更取消旧代次，迟到结果不能覆盖新配置。按需采集在最后订阅释放后停止；显式持续采集模式在无客户端时仍运行，用于后续历史与告警。

客户端采用受现有会话/项目权限保护的快照与订阅接口。一个页面提交去重后的资产需求，服务器返回有代次/序号的全量或增量快照；断线重新同步，慢客户端缓冲有界。前端保留 `RuntimeAssetConnection` 消费接口，使二维、三维和 M4 事件继续使用同一状态。服务端能力声明区分集中模式和既有即时模式，不静默回退后仍宣称集中采集。

凭据、有效地址、认证头与证书由服务器环境解析；项目定义只保存逻辑引用，浏览器不接收其值。环境凭据须绑定允许的端点/项目，防止把凭据发送给任意新地址。当前完整 data-source config 和运行 sourcePath 出口要随适配分层，标准运行响应不再暴露有效内网地址、认证头或原始字段路径。连接测试复用相同解析、请求限制与脱敏，不另开宽松通道。

## 顺序与首项验收

1. 本地 Node API/静态宿主与 SQLite/ObjectBucket 适配：事务 CAS、外键、准确 changes、资源读写、会话权限和已有项目 API 实测；空目录按迁移启动，兼容 Worker 保留。
2. REST 源采集/标准化分离，集中调度与需求订阅；两个独立客户端、两个资产共用源，用上游计数证明每周期一次请求。关闭一个客户端不断流，最后按需订阅退出后停止。
3. 超时、失败重试、陈旧与恢复、配置代次、持续采集和重启恢复；旧值不伪装在线。环境凭据与浏览器/日志出口验证。
4. WebSocket 上游认证、心跳、订阅恢复与有界消息，进入同一标准缓存/推送层；MQTT/SQL 在 M6b 扩展。

验收使用本地真实 HTTP/WebSocket 协议服务和独立浏览器客户端，记录请求数量、最后释放、故障恢复与配置更换的迟到响应。公司现场接口和目标硬件仍单列待验证。M6a完成后直接进入M5，不关闭完整引擎目标。
